Scopes follow a **family model**: `<family>:read` or `<family>:write`, where **write implies read** within the same family. Request the **minimum** scopes your integration needs — during the OAuth flow (space-separated `scope` parameter on [`/oauth-authorize`](/oauth/authorize)) or when creating an API key in the dashboard.

Today the REST API surfaces the `crm` and `webhooks` families; the other families gate [MCP tools](/mcp/overview). As REST endpoints expand into those domains they will use the same scope strings.

On the MCP server, every tool is mapped to one family scope: `tools/list` shows only tools your credential satisfies, and the scope is re-checked on every `tools/call`.

## Legacy scopes

The original scope strings predate the family model. They keep working — each maps onto its family, so **existing Zapier connections and API keys are unaffected**:

<SchemaTable title="Legacy aliases" rows={[
  { name: "contacts:read", type: "legacy", description: "Satisfies crm:read." },
  { name: "contacts:write", type: "legacy", description: "Satisfies crm:write (and therefore crm:read)." },
]} />

New integrations should request the family scopes; error messages name the family scope (e.g. `crm:write`) even when your credential holds the legacy alias.

## Example

```text
scope=crm:read%20crm:write%20webhooks:write
```

<Callout type="tip">
A Zapier-style integration that lists contacts, creates contacts, and subscribes to triggers needs <code>crm:read crm:write webhooks:write</code> (write implies read, so <code>webhooks:read</code> comes along automatically).
</Callout>

## Scope errors

Calling an endpoint without a satisfying scope returns HTTP `403`:

```json
{
  "error": "forbidden",
  "message": "crm:write scope is required."
}
```
